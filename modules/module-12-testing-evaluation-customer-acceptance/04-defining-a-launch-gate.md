# Tutorial 12.4 — Defining a Launch Gate

**Created by School of AI**

**Module:** Testing, Evaluation & Customer Acceptance

## Why this matters
Forward deployed engineering combines software delivery with customer problem solving. The technical answer is only useful if it fits the workflow, constraints and operating environment.

## Step 1 — Start with evidence
Collect evidence from the real workflow, users, systems, data, baseline metrics and stakeholder feedback. Do not design solely from the first feature request.

## Step 2 — Convert ambiguity into a deliverable
State:
- customer/user
- current workflow
- problem
- baseline
- desired outcome
- systems/data
- constraint
- success metric
- smallest useful release

## Step 3 — Make tradeoffs explicit
Balance scope, speed, quality, reliability and maintainability. Record what you accepted and what evidence would make you revisit the choice.

## Step 4 — Build a short learning loop
**Hypothesis → Prototype → Customer Demo → Evidence → Decision**

Do not wait until the end to learn that the user does not care about the workflow you automated.

## Step 5 — Preserve the path to production
Even in a rapid POC, track identity, data sensitivity, integrations, errors, evaluation, logging and deployment assumptions.



## Field exercise
Write a one-page customer note with:
1. observed workflow,
2. root problem,
3. current baseline,
4. proposed intervention,
5. key technical risk,
6. next experiment,
7. success evidence.

## Review questions
- Why is this the right problem?
- What is deliberately out of scope?
- Which risk should be retired first?
- What would the customer measure?
- What changes if a key dependency is unavailable?
